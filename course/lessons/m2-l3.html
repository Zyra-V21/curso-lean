Decidir y repetir: if, match y recursión

En una frase: las definiciones eligen un camino según el caso y repiten llamándose a sí mismas; tú las sigues a mano, caso por caso, como quien sigue una receta.

Por qué te importa: los errores más típicos viven en los casos: la lista vacía, el límite (¿el 100 entra o no?), el último paso. Si sabes seguir una definición a mano, los encuentras tú antes que nadie.

Si pasa esto, una cosa; si no, otra

Con if ... then ... else una función elige un camino. Esta comisión cobra 1 a las cantidades pequeñas y el 1 % al resto:

#eval fee 50   --> 1
#eval fee 100  --> 1
#eval fee 250  --> 2

Mira fee 100: ¿100 es menor que 100? No. Así que va por el else: 100 / 100 = 1. En los límites es donde hay que mirar con lupa.

Para decidir, Lean calcula la condición y obtiene un Bool: true o false, en minúscula, valores para calcular. True y False, en mayúscula, son proposiciones: cosas que se afirman. Se parecen, pero no son lo mismo:

#check true   --> Bool.true : Bool
#check True   --> True : Prop

Según la forma: match

Con match una función mira qué forma tiene el dato y elige un caso. Cada caso empieza con una barra |:

#eval describe 1  --> "one"
#eval describe 5  --> "many"

Repetir: una función que se llama a sí misma

Esta función suma todos los números desde 1 hasta el que le pidas. Para eso se llama a sí misma con un número más pequeño. Eso se llama recursión.

Se sigue a mano desenrollándola, un paso cada vez, hasta llegar al caso base:

sumTo 3
= 3 + sumTo 2
= 3 + (2 + sumTo 1)
= 3 + (2 + (1 + sumTo 0))
= 3 + (2 + (1 + 0))
= 6
#eval sumTo 3  --> 6

Listas: el primero y el resto

Una lista son varios datos en fila, entre corchetes: [5, 10, 20]. La lista vacía es []. Para recorrerla, un match separa el primer elemento del resto:

#eval total [5, 10, 20]  --> 35

A mano: 5 + total [10, 20], luego 5 + (10 + total [20]), luego 5 + (10 + (20 + total [])), y el caso base pone el 0 final: 35.

Ojo de auditor: si la IA hubiera escrito | [] => 1 en el caso base, todos los totales saldrían con 1 de más. Lean no se quejaría: es una definición válida, solo que no es la suma. Los casos base y los límites son lo primero que se revisa.

Lean exige que la repetición termine

Una función que se llama a sí misma tiene que acabar algún día. Lean lo comprueba, y si no ve que termina, rechaza la definición en rojo: fail to show termination («no consigo demostrar que termina»).

La IA puede saltarse esa comprobación escribiendo partial def:

partial def countdown (n : Nat) : Nat :=
  if n = 0 then 0 else countdown (n - 1)

#eval countdown 5  --> 0

Lean calcula con ella sin problema, pero la trata como una caja negra: no puede demostrar nada sobre lo que hace por dentro. Ni siquiera que countdown 0 es 0, aunque salte a la vista.

partial no es una trampa como sorry: con él no se pueden demostrar cosas falsas. Pero si un teorema importante habla de una función partial, probablemente dice muy poco sobre ella. Pregunta por qué no se demostró que termina.

Llévate esto

  • if ... then ... else elige un camino según una condición. Mira siempre los límites: ¿el 100 entra o no?
  • match y la recursión se siguen a mano, caso por caso, hasta el caso base. Ahí es donde más errores se esconden.
  • partial def es una caja negra: Lean calcula con ella, pero no demuestra nada sobre ella.
