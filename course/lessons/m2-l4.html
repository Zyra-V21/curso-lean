Estructuras: datos con campos (y con promesas)

En una frase: una structure agrupa varios datos con nombre, y algunos de sus campos no son datos sino promesas que alguien tuvo que demostrar.

Por qué te importa: el teorema del jefe esconde todas sus hipótesis dentro de una estructura, WhirAccept. Si no sabes leer estructuras, no ves qué se está dando por supuesto.

Un registro con campos

Una estructura es como una ficha con casillas fijas. Esta describe una cuenta: de quién es y cuánto saldo tiene. Toca las piezas:

Para leer un campo se usa un punto: alice.balance se lee «el balance de alice».

#eval alice.balance  --> 10
#eval alice.owner    --> "alice"

El punto también sirve para llamar a una función del tipo del dato. Si xs es una lista, xs.length es lo mismo que List.length xs: su longitud.

def xs : List Nat := [5, 10, 20]
#eval xs.length       --> 3
#eval List.length xs  --> 3

En el jefe verás finalPoly.length o acc.finalRand.reverse: son funciones llamadas con punto (longitud, darle la vuelta a la lista).

Copias con cambios, y el atajo ⟨⟩

En Lean los datos no se modifican: se hacen copias. { alice with balance := 5 } es «una copia de alice con el saldo cambiado a 5». La alice original no cambia:

def alice2 : Account := { alice with balance := 5 }
#eval alice2.balance  --> 5
#eval alice2.owner    --> "alice"
#eval alice.balance   --> 10

Hay un atajo para construir: los ángulos ⟨ ⟩ rellenan los campos en el orden en que se declararon, sin decir sus nombres:

def bob : Account := ⟨"bob", 20⟩
#eval bob.balance  --> 20

Ojo de auditor: con ⟨ ⟩ el orden importa y no se ve. Solo sabes qué es cada cosa si miras la structure. Si dos campos son del mismo tipo (por ejemplo, dos Nat), ⟨5, 8⟩ y ⟨8, 5⟩ son válidos los dos y significan cosas distintas. Lean no avisa.

Campos que son promesas

Aquí viene lo importante. Un campo puede tener como tipo una proposición. Entonces no guarda un dato: guarda una demostración de que esa proposición es verdad.

def five : PositiveAmount := ⟨5, by decide⟩
#eval five.value  --> 5

by decide es la demostración: Lean calcula que 0 < 5 es verdad. ¿Y con un 0?

def zero : PositiveAmount := ⟨0, by decide⟩

Lean se niega, en rojo: 0 < 0 es falso. No hay manera de construir un PositiveAmount con un 0. Por eso, si tienes uno en la mano, sabes seguro que su value es mayor que 0: alguien tuvo que demostrarlo para construirlo.

¿Quién garantiza la promesa?

Una transferencia válida promete que la cantidad no pasa del saldo. Y un teorema (lo verás a fondo en el módulo 3) dice algo sobre ella:

Sin la promesa sería falso. Con saldo 5 y cantidad 8, en Nat la resta 5 - 8 da 0, y 0 + 8 = 8, no 5:

#eval 5 - 8 + 8  --> 8

La pregunta de auditor: el teorema solo habla de transferencias que cumplen la promesa. ¿Quién garantiza que el sistema real solo crea transferencias así? Si el contrato real no comprueba amount ≤ balance antes de restar, el teorema no dice nada de ese caso. Lean no puede saberlo: eso lo miras tú, en el código real.

inductive: una lista cerrada de opciones

A veces un dato solo puede ser una de unas pocas opciones. Para eso está inductive:

Una función sobre Status usa un match con un caso por opción:

def isFinal : Status → Bool
  | Status.pending => false
  | Status.accepted => true
  | Status.rejected => true
#eval isFinal Status.accepted  --> true

Un detalle que ayuda al auditor: si un match sobre un Status se olvida de una opción, Lean da un error y dice cuál falta (Missing cases).

Pero ojo con _: si el match acaba en | _ => ..., ese caso se traga en silencio todas las opciones que falten, y Lean no avisa. Cada _ es un sitio que mirar: ¿qué casos está recogiendo, y es correcto lo que devuelve para todos ellos?

El jefe: WhirAccept

Hoy despejas casi toda la estructura WhirAccept. Fíjate en sus tres últimos campos: hlen, opens e identity. No son datos: son promesas, igual que pos en PositiveAmount.

Son las hipótesis del teorema, escondidas dentro de la estructura. El teorema viene a decir: «dame un WhirAccept y te garantizo...». La pregunta de hoy aplica aquí: ¿quién garantiza que el verificador real, el de Solidity, solo acepta cuando se cumplen esas tres promesas?

Llévate esto

  • Una structure agrupa campos con nombre. x.campo lee un campo y { x with campo := ... } hace una copia cambiada. Con ⟨ ⟩, el orden de los campos manda.
  • Un campo cuyo tipo es una proposición es una promesa: para construir el valor, alguien tuvo que demostrarla.
  • Un teorema que recibe una estructura con promesas las da por supuestas. Pregunta siempre quién las garantiza en el sistema real.
